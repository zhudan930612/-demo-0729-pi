## When to Use
用户提出新需求、一次包含多个需求点、或对既有需求做变更时；用户说"提需求/做需求/梳理需求/需求沟通/需求收集"等进入需求收集对话。进入前先做需求分级（标准见 references/collection-rules.md 第 0 节）：一次性原型建议直接 Vibe 不入本技能；小型局部功能走轻量模式；跨模块/支付权限隐私/多人多 Agent 走完整模式。不在编码实现阶段使用（那是开发流程技能/O1 的职责）。

## Procedure
1. 需求分级（开场先行）：判断任务类型——一次性原型 / 小型局部功能 / 跨模块或敏感功能，标准见 references/collection-rules.md 第 0 节；一次性原型建议直接 Vibe 不入本技能；分级结论向用户说明，用户可要求升级力度
2. 完整模式开场：理解业务目标，倾听用户叙述，实时识别需求点并编号，建立 A2 需求点清单；轻量模式：只确认范围、非目标与 3-5 条核心验收标准（执行细则见 references/collection-rules.md 第 0.3 节）
3. 逐需求点处理：按模板 B1-B4 检查覆盖，缺什么自然追问什么（不逐题表单式提问）
4. 全程应用歧义对抗规则（见 references/collection-rules.md）：量化模糊词、确认术语定义、必问异常路径、确认范围边界、收口前问隐含假设
5. 需求点收口：向用户展示该需求点的收口摘要（B1-B4 要点），用户确认后才算该点收口
6. 多需求点管理：实时维护 A2 清单，检测需求点间依赖/互斥/重复冲突，冲突时追问用户确认以哪个为准
7. 用户表示无更多需求点或确认 A2 清单完整后，生成需求文档（模块 A/B/C，按 templates/requirement-template.md 结构；轻量模式允许跳过非核心模块）
8. 执行定稿自检清单（硬性环节，见 references/collection-rules.md 第 8 条）：逐条自查——每条验收项是行为断言？术语无同词异义？B3/B4 一一对应全覆盖？异常/边界路径已覆盖？数据依赖明确？每条验收项有明确验证路径（自动化或人工）且归属判定清楚？测试边界（seams）已确认？自检不过继续追问修订，通过才进入下一步
9. 逐节展示文档给用户确认；用户确认无歧义后定稿：同时产出需求文档 + 独立验收清单（templates/acceptance-checklist.md 结构，验收项编号与文档 B3/B4 一一对应），按落盘约定存储（项目既有约定优先，默认见 references/collection-rules.md 第 8 条）；**术语同步**：若 A3 术语表有新增/修订 → 增量同步到项目 CONTEXT.md 术语表（项目既有约定优先，默认根目录 CONTEXT.md；无术语变化则跳过，不为写而写），技能结束
10. 定稿后的需求变更：回到技能重新走变更确认流程，更新对应章节和确认记录（A4）；改 B3/B4 必须同步改验收清单，不静默修改；变更前先归因——是实现偏离规格（开发问题，回开发修实现、规格不动），还是规格落后于真实需求（规格问题，更新规格再继续），归因结论记入 A4；**长期资产同步**：变更涉及术语口径 → 同步 CONTEXT.md 术语表 + 受影响需求文档（不留过期条目）；变更涉及架构决定（以后难改 + 有明显取舍）→ 新增 docs/adr/NNNN-<slug>.md 一条，被替换的旧 ADR 标"已替换"

## Pitfalls
- 禁止写代码、禁止给出具体实现方案：架构约束（C1）只写边界，不写技术选型
- 禁止替用户决定：任何歧义必须追问，不猜测
- 验收项必须是可观察行为断言（点击 X 出现 Y），拒绝快速/简单/直观等形容词
- 多需求点必须编号并检测重复冲突，两个点说同一件事的不同版本要追问确认
- 术语复用必须同义：同一概念在不同需求点出现时检查 A3 定义一致性
- 定稿前必须逐节确认，不得一次性甩出整篇文档等用户自己挑错
- 对话中收集的信息必须落进文档结构，不允许只聊不记
- 禁止一刀切：所有需求都跑完整流程（小需求过重），或一律轻量（跨模块/敏感需求过轻）——先分级再定力度
- 轻量模式不是免检：跳过的只是非核心模块，留下的验收项仍必须是行为断言且可验证
- 术语口径变化必须同步 CONTEXT.md（项目既有约定优先）与受影响需求文档，禁止只改需求文档留过期条目；ADR 只记"以后难改 + 有明显取舍"的决定，不为写而写
- 定稿自检清单是硬性环节，不得跳过直接给用户确认
- 验收清单是 B3/B4 的派生导出：定稿时与文档同时产出，编号一一对应，变更必须同步，禁止只改文档不改清单
- 禁止自动调用 review-requirements：用户会自己说'审查需求文档'来触发该技能，本技能只负责收集与定稿

## Verification
1. 定稿文档覆盖模块 A（A1-A4）、B（每个需求点 B1-B4）、C（C1-C5）全结构
2. 每条验收项可测试：行为断言 + 含正常/异常/边界路径 + 标注验证层级
3. 每条验收项在'如何测试'（B4）中有对应验证方式
4. 术语表（A3）覆盖对话中出现的关键概念，无同词异义
5. 确认记录（A4）带日期，记录每轮关键确认
6. 完成定义（C5）明确：哪些验收项全部通过才算完成
7. 定稿自检清单已执行且通过（行为断言/术语一致/需求点↔验收项覆盖/B3B4 全覆盖/异常路径/数据依赖/验证路径归属/seams 确认）
8. 用户逐节确认过文档且无歧义
9. 定稿同时产出需求文档 + 独立验收清单，验收项编号与 B3/B4 一一对应
10. 不输出任何代码或实现方案
11. 分级结论正确：原型/小功能/跨模块/敏感类型判断与任务实际匹配，且已向用户说明
12. A3 术语新增/修订已同步 CONTEXT.md（或确认项目无术语表约定）；术语变更时 CONTEXT.md 与受影响需求文档无过期条目
