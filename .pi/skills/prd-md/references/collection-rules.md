# 歧义对抗细则（对话收口规则层 2）

本文件是 prd-md 技能的核心细则。对话全程持续应用，不逐题表单式提问，缺什么补问什么。

## 0. 需求分级细则（进入对话前先行）

### 0.1 Vibe/Spec 切换信号

出现下面任意两三项 → 必须走 Spec（完整或轻量），只靠聊天不够：

1. 要修改多个模块或很多文件
2. 有权限、支付、隐私或数据安全要求
3. 存在很多边界情况和失败情况
4. 需要多人或多个 AI 会话继续开发
5. 预计几周后还要维护
6. 用户开始频繁说"这个前面不是讲过了吗"
7. 功能能运行，但没人知道是否已经完整实现

### 0.2 分级表

| 任务类型 | 推荐方式 | 最少需要留下什么 |
|---|---|---|
| 一次性原型（几小时后丢弃的草图/试验） | Vibe Coding，不入本技能 | 一段说明目标和临时边界的提示词 |
| 小型局部功能 | 轻量 Spec | 范围、非目标、3-5 条验收标准 |
| 跨模块功能 | 完整 Spec | 需求文档 A/B/C 全结构 + 验收清单 |
| 支付、权限、隐私 | 完整 Spec + 人工审查 | 威胁与失败场景、审计要求、验证证据 |
| 多人或多 Agent 开发 | 完整 Spec + 版本管理 | 明确依赖、负责人、变更记录 |

判断口诀：换一个完全没看过当前聊天的人，只读仓库文档能否继续开发并判断完成？不能 → 至少轻量 Spec。

### 0.3 轻量模式执行规则

- 场景：小型局部功能。允许跳过 A4 确认记录、C3/C4（无数据依赖/非功能要求时）、B2 精简为核心路径；B3 只留 3-5 条核心验收项（正常 + 关键异常）
- 不允许省略：行为断言性质（每条仍是"点击 X 出现 Y"）、非目标（C2 一句话）、验收项的可验证路径（B4 对应）
- 轻量不是免检：留下的验收项必须通过定稿自检清单的行为断言检查
- 分级结论要向用户说明；用户可要求升级为完整流程

## 1. 量化规则（模糊词拦截表）

**判定原则**：任何词如果无法直接写出对应的测试断言形式，就必须追问。下表是高频高危触发词，不限于此表。

| 类别 | 触发词（用户原话） | 追问动作 |
|---|---|---|
| 时间 | 快速 / 尽快 / 及时 / 立即 / 马上 / 实时 / 最新 | 追问具体时限或刷新频率（"3 秒内"、"每 5 分钟"） |
| 数量 | 大量 / 很多 / 海量 / 所有 / 任何 / 全部 | 追问数量级/上限，或全量范围是否真实覆盖 |
| 主观 | 友好 / 直观 / 简单 / 好看 / 合理 / 适当 | 追问具体可观察行为（"展示什么、怎么展示"） |
| 精度 | 差不多 / 大概 / 左右 | 追问精确值或允许误差范围 |
| 状态 | 正常 / 异常 | 追问各自的判定标准 |
| 范围 | 其他 / 等 / 等等 / 类似 / 相关 | 追问具体清单（"具体指哪些？列全"）——隐藏范围蔓延，最需警惕 |
| 能力 | 支持 / 可以 / 允许 | 追问是必须还是可选、不支持时怎么办 |
| 默认 | 默认 / 默认情况下 | 追问默认值是什么、谁能改 |
| 按需 | 按需 / 可选 / 视情况 / 必要时 | 追问触发条件 |
| 沿用 | 沿用 / 复用 / 保持现状 / 和之前一样 / 不变 | 追问具体指哪个行为、引到哪个既有功能（项目实践里最危险，必须落到具体编号/位置） |

原则：**任何无法观察、无法测试的描述都必须转成行为断言或指标；无法转的必须追问。**

## 2. 术语规则

- 关键概念**首次出现**时，立即追问定义并记入 A3
- 后续复用同一词时检查是否同义；用户换了说法说同一件事时，确认并统一到 A3 术语
- 同一需求点内，术语与口语混用（如"保单"和"保险单"）时，确认是否同一概念
- 一次多需求点时，跨需求点检查术语一致性——两个点用同一个词指不同东西，是最高危歧义

## 3. 异常规则

每个需求点收口前必问三类异常：
1. **数据异常**：数据为空 / 缺失 / 格式不符 / 上游失败时，界面与行为如何
2. **权限异常**：无权限 / 越权操作时如何（按需，非每需求必问）
3. **过程异常**：加载中 / 刷新 / 部分失败 / 重试时如何

异常路径必须进入 B3 验收项（异常/边界覆盖列），不能只写正常路径。

## 4. 边界规则

- 每个需求点收口前确认"明确不做的是什么"（入 C2）
- 范围涉及版本时（V1/V2），确认本期边界与延后项的触发条件
- 用户描述功能时夹带"顺便""以后"等词 → 追问：本期做还是延后？延后入 C2

## 5. 隐含假设规则

收口时主动问：
- "还有什么默认行为没说？"（如：无数据时显示什么、默认选中什么）
- "这个功能依赖哪些现有功能/数据？"（补 C3 与 A2 依赖关系）
- "谁能用这个功能？"（按需补 C4 权限）

## 6. 多需求点管理细则

- 实时维护 A2 清单：新需求点出现立即编号（R1、R2…）
- 编号顺序按出现顺序，不按优先级；优先级单独标注
- 检测关系：依赖（B 依赖 A 的数据/功能）、互斥（模式互斥）、独立
- 检测重复冲突：两个需求点描述同一功能的不同版本 → 停下，向用户展示差异，确认以哪个为准，冲突结果记入 A2 与 A4
- 每个需求点收口后，向用户复述该点摘要（B1-B4 要点），用户确认后才处理下一个点

## 7. 收口判定

需求点满足全部条件才算收口：
- B1：一句话能说清做什么，无模糊词
- B2：说清了谁操作、怎么操作、看到什么，核心路径已标注
- B3：每条是行为断言且含三要素——对象（对什么操作）/ 动作（做什么）/ 预期结果（出现什么、具体到数值/内容/状态）；列表/数据展示类必须明确字段集、排序规则、分页/加载方式、空态（无数据时显示什么）；粒度合适（一条一个可独立验证的行为，"和"连接多行为的要拆，一条描述整个页面的要拆，同一行为不同前置条件可合并为边界列）；正常+异常/边界路径都有，验证层级已标注
- B4：每条验收项有对应验证方式与证据标准；测试边界（seams）已与用户确认并冻结——每个模块的公共接口/测试边界明确，测试只在这些 seam 上写，不测内部实现

不满足则继续追问，不进入下一个需求点。

## 8. 定稿收口

1. 用户表示无更多需求点，或确认 A2 清单完整
2. 生成完整文档（A/B/C 全模块，按 templates/requirement-template.md）
3. 执行定稿自检清单（硬性环节，不得跳过）：
   - 每条验收项是可观察行为断言（点击 X 出现 Y），无形容词
   - 术语表 A3 覆盖对话中的关键概念，无同词异义
   - B1 每条需求点都有 B3 验收项覆盖（反向覆盖度：需求点 ↔ 验收项一一对应；验收阶段不再依赖人为补漏）
   - B3 每条验收项在 B4 中有对应验证方式（一一对应全覆盖）
   - 异常/边界路径已覆盖（空数据/缺失/失败/无权限）
   - C3 数据依赖明确：数据源/格式/许可归因/就绪状态（真实或 mock）
   - 每条验收项有明确验证路径（自动化或人工），归属判定清楚
   - 测试边界（seams）已确认并冻结：每个模块的公共接口/测试边界明确，与用户确认过，编码时按此写测试
   - C5 完成定义与验收项一致
   - 自检不过 → 继续追问修订，直到通过；不得携带未决项进入用户确认
4. 逐节展示确认（不是一次性甩出整篇）
5. 用户确认无歧义 → 定稿：同时产出需求文档 + 独立验收清单（templates/acceptance-checklist.md），验收项编号与文档 B3/B4 一一对应；验收清单作为验收 agent 的输入与验收执行记录
   - 落盘约定：先检查项目既有约定（AGENTS.md / docs README），有则遵循；无则用默认——需求文档 `<项目文档目录>/requirements/<名称>-V<N>需求.md`，验收清单 `<项目文档目录>/requirements/<名称>-V<N>验收清单.md`（同目录同名前缀，保持编号绑定）；名称与版本号定稿时与用户确认
6. 定稿后需求变更：重新走变更确认流程，更新对应章节与 A4；改 B3/B4 必须同步改验收清单，不静默修改。**变更先归因**：发现"需求与实现不一致"时，先判断是实现偏离规格（开发问题，回开发修实现、规格不动），还是规格落后于真实需求（规格问题，更新规格再继续）；归因结论记入 A4

## 9. 人工验证规则

验证层级四类：[单测] / [数据脚本] / [E2E-自动化] / [E2E-人工]。

**必须人工（[E2E-人工]）的验收项**：
- 主观视觉/审美：配色、动画手感、布局舒适度（AI 可测帧率/断言，但"感觉正确"是人的判断）
- 真实渲染目视确认：地图瓦片拼接、注记位置、图层叠加、canvas/WebGL 绘制效果
- 真实交互与真实环境：headless 无法触发的交互、真实账号/权限/外部服务/真实网络（mock 跑通 ≠ 真实环境跑通）
- 业务合理性：数值正确但业务上是否荒谬、术语/文案是否准确像人话
- 最终用户接受（UAT）：用户走一遍真实工作流确认

**人工验证证据标准**（与自动化同等严格）：
- 验证人：用户本人或指定验收人；AI 无资格自称人工验证（AI 自跑 UI 点验 = 冒烟，不算验证）
- 操作步骤：逐步写清（打开页面 → 点 X → 观察 Y）
- 观察结果：符合/不符合哪条验收项
- 记录：截图/录屏（强烈建议）
- 确认：验证人确认 + 日期，入验收报告

**规则**：自动化优先；人工验证是受控的最后手段。需求阶段（自检清单）必须判定每条验收项归属，归属不清的验收项须改写。
