## When to Use
用户在需求沟通/审查阶段要求检查需求文档（REQUIREMENTS.md 或 docs/requirements/*.md）质量时；需求定稿交给实现前做独立验收；grill-me 拷打后补一道结构化自检；需求文档与现有实现、数据源口径疑似脱节时。

## Procedure
1. 按 8 个维度逐项扫描整个需求文档，输出 findings（位置+严重度+问题+建议），不重写需求文本
2. 维度1 问题清晰度：问题陈述是否含解决方案/技术选型（如'React 应用'），是否与需求列表混在一起
3. 维度2 可测试性：每条需求（必须/应该/可以）是否有验收标准——Given/When/Then 或可测指标，拒绝'快速/简单/直观'式形容词
4. 维度3 约束清单：真实约束（预算/时间/依赖/数据源限制）是否与未验证假设分离
5. 维度4 范围边界：V1 内/外是否明确、延后项是否有重新考虑触发条件、是否描述最小可用版
6. 维度5 需求标识：编号是否唯一连续（保持文档自身惯例，不必强推 R-NN）、交叉引用是否用编号而非自由描述
7. 维度6 开放问题：是否有开放问题部分，每条是否有解决计划或负责人
8. 维度7 农险业务场景（用户硬性要求）：每条需求能否回答'这个功能在农险业务里解决什么问题'——站在防灾减损/查勘调度预判/承保风险评估表述，禁止纯技术/可视化角度
9. 维度8 与实现/数据源一致性：需求口径与 git log、现有代码、数据源实测核对（如降水=Open-Meteo ECMWF IFS 0.25°、8787 服务、时次语义等），防文档与现状脱节
10. 汇总：全部通过则确认'需求文档满足所有维度，可进入实现'；有缺口则列出 findings 交给作者修复

## Pitfalls
- 只审查不重写：禁止代写需求文本/验收标准/问题陈述，也不得因审查而开始写实现代码（用户最高优先级纪律：用户明确说进入实现前不动手）
- 不新增范围：不得发明缺失需求或扩展文档范围
- 只评文档本身：不基于外部知识添加'应该有什么'的发现
- 不要强制 R-NN 编号：若文档惯例是编号列表（REQUIREMENTS.md 的 numbered list），保持惯例，只检查唯一性与可交叉引用
- 需求文档必须收敛为单一规格源，发现需求分散多文档时要指出合并
- 审查表述必须站在农险业务场景，不能只从技术/可视化角度提意见
- 涉及数据/口径的发现必须实测或核对（git log、代码、API），不能凭记忆断言

## Verification
1. 每条需求都能回答'在农险业务里解决什么问题'
2. 每条必须有需求有可测试的验收标准（Given/When/Then 或指标）
3. 问题陈述无技术选型/解决方案语言
4. 范围（V1 内/外）、约束、开放问题均有明确边界
5. 需求口径与实现/数据源一致（已用 git log/代码/实测核对）
6. 输出为 findings 列表或'文档就绪'确认，无重写行为
