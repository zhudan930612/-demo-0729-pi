# 服务端数据持久化计划

> 状态：计划（待实施）
> 日期：2026-07-31
> 触发背景：部署后作为内部人员日常核查使用，人工新增地块、筛选隐藏记录、种植档案覆盖不能只保存在浏览器 localStorage，需服务端持久化。

## 1. 背景与目标

当前 Demo 定位是「纯静态、无后端」：人工地块、隐藏记录、种植档案覆盖全部写浏览器 `localStorage`，按 origin 隔离，换浏览器/清数据即丢（本次排查已实际触发一次，数据在 `localhost:5173` 与 `127.0.0.1:5173` 间不可见）。

部署场景（内部人员日常核查）要求三类编辑数据**跨设备、跨浏览器、跨会话持久化**。

目标：

- 三类编辑数据（人工地块 / 隐藏记录 / 种植档案覆盖）落服务端数据库。
- AI 地块 GeoJSON 与吉林一号影像**保持静态文件**，不上服务端数据库（受限数据边界不变）。
- 地图、绘制、筛选、详情等既有交互代码不改行为。

## 2. 现状与接缝

三个存储模块均以「整库 JSON + villages map」形态读写，且都接受 `storage?: Storage` 注入，默认 `window.localStorage`：

| 模块 | 内容 | 数据形状 |
|------|------|---------|
| `web/src/utils/manualParcelStorage.ts` | 人工地块 | `{version:1, villages:{村:[Feature]}}` |
| `web/src/features/parcels/parcelHiddenStorage.ts` | 隐藏 ID | `{version:1, villages:{村:{datasetVersion, hiddenIds}}}` |
| `web/src/features/policy/cultivationStorage.ts` | 档案覆盖 | `{version:1, villages:{村:{overrides, additions}}}` |

调用点（`MapView.vue` 等）多数未传 `storage` 参数，直接用默认 `window.localStorage`。

### 决策：内存镜像 + 异步 flush + 服务端按村合并（审查修正版）

不重写三个模块的读写逻辑。核心约束：`Storage` 接口是同步契约（`getItem(): string|null` / `setItem(): void`），而 HTTP 只有异步，**远程 Storage 适配器在接口层面不成立**（fetch 无法同步，同步 XHR 已废弃）。因此采用「内存镜像 + dirty 队列 + flush」：

```
remoteStorage（提供同步 Storage 形状的内存镜像）
├── preload()：启动时 async 拉取 3 个 key 全库 JSON → 内存 Map<key, string>
├── getItem(key)：同步读内存（未预取或失败返回 null，由模块原有逻辑按空处理）
├── setItem(key, value)：同步写内存 + dirty.add(key)
├── removeItem(key)：同步删内存 + dirty 标记
├── flush()：await PUT 全部 dirty key；失败保留 dirty 并全局报错
└── 状态：ready / loading / error（error 时全局可见，绝不静默空数据）
```

读取路径零改动（同步读缓存）；写入路径把「保存动作」改为 `await flush()` 后才提示成功。

并发策略由服务端保证：**同一村整村覆盖，不同村互不影响**（服务端把 villages map 按村拆行存，合并时只替换目标村）。同一村并发编辑按最后写入胜出，内部低频场景可接受；API 返回 `updated_at`，为后续乐观锁预留。

## 3. 技术选型

- 后端：**Node + Express**（与前端同语言、轻量；Fastify 为备选，不阻塞实施）。
- 数据库：**SQLite（better-sqlite3）**，单文件零运维；每村每类数据一行（村代码 + JSON），不引入空间数据库。
- 部署形态：**同源**——Node 服务托管 `web/dist` 静态文件并提供 `/api/*`，单一端口，避免 CORS。
- 环境开关：前端通过 Vite env（如 `VITE_STORAGE_MODE=remote|local`）切换存储实现，本地开发默认 `local`，部署默认 `remote`。

## 4. 数据模型（SQLite）

```sql
CREATE TABLE manual_parcels (
  village_code TEXT PRIMARY KEY,
  payload TEXT NOT NULL,        -- ManualParcelFeature[] 的 JSON
  updated_at TEXT NOT NULL
);
CREATE TABLE parcel_hidden (
  village_code TEXT PRIMARY KEY,
  dataset_version TEXT NOT NULL,
  hidden_ids TEXT NOT NULL,     -- ParcelId[] 的 JSON
  updated_at TEXT NOT NULL
);
CREATE TABLE cultivation_overrides (
  village_code TEXT PRIMARY KEY,
  overrides TEXT NOT NULL,      -- Record<businessKey, CultivationRecord>
  additions TEXT NOT NULL,      -- 同上
  updated_at TEXT NOT NULL
);
```

## 5. API 契约

通用存储代理接口（一个 key 一条路由，内部按村合并）：

- `GET /api/storage/:key` → 返回该 key 合并后的完整 JSON 字符串（`getItem` 语义；无数据时 `404` 或返回空串）
- `PUT /api/storage/:key` → 请求体为完整 JSON 字符串；服务端解析 villages map，按村 upsert；返回 200
- `DELETE /api/storage/:key` → 清空该 key 全部数据（预留，前端当前不用）

服务端实现要点：

- `:key` 白名单限定 `manual-parcels:v1 | parcel-edits:v1 | cultivation-overrides:v1`，防注入。
- 写入前做最小 schema 校验（version 字段、villages 为对象、村庄数组/对象形状），**几何与业务规则校验复用前端逻辑移植**（见 §7）。
- 所有写操作先校验后落库，失败返回 4xx 与中文错误信息。

## 6. 前端改动清单（审查修正版）

1. 新增 `web/src/api/remoteStorage.ts`：内存镜像 + dirty 队列 + `preload()/flush()`；`flush` 内 `PUT /api/storage/:key`，网络失败/4xx/5xx 归一到 `{ok:false,error}`，同时置全局 `error` 状态（复用 `showNotice` 类提示，不得静默）。
2. 新增 `web/src/utils/storageProvider.ts`：按 `VITE_STORAGE_MODE`（local|remote）返回单例 `localStorage` 或 `remoteStorage`；**remote 模式 API 不可达时禁止回退 localStorage**（避免多人数据分裂），只置 error 状态。
3. 三个存储模块的默认存储改为调用 `getDefaultStorage()`（spec 传入的 mock storage 优先级仍最高）。
4. **保存动作异步化（5 处）**：`saveParcelEdits`（现同步）改 async；`saveManualBatch`（已 async）末尾加 `await flush()`；`saveCultivationRecord`、`removeCultivationRecord`、`requestRestoreCultivation` 改 async 并在写成功后 `await flush()`。flush 失败保留编辑现场与 dirty，不退出编辑模式。
5. 应用入口调用 `preload()`（App 挂载或首次进村前），失败时全局提示「服务端存储不可用」并显示重试。
6. 保存提示文案去本地化：「已保存到当前浏览器」改为「已保存」。

## 7. 服务端校验

- 移植 `web/src/utils/parcelGeometry.ts` 的几何校验（自相交、顶点数、闭合、零面积）与 `manualParcelStorage.isManualFeature` 字段校验到 `server/`（共享同一份 TS 源码或复制并锁定版本）。
- 档案校验移植 `web/src/features/policy/cultivationState.ts` 的 `validateCultivationRecords` 及 `CultivationRecord` 类型依赖（季节枚举、期间不重叠等）。
- 隐藏 ID 列表校验：字符串数组、村代码匹配。
- 服务端校验通过后才落库；不信任前端。
- `updated_at` 随每次写入更新并在 GET 响应中返回，为乐观锁预留。

## 8. 数据迁移

- 部署后首次上线可接受从空库开始；如需迁移既有 localStorage 数据，提供一次性浏览器脚本：读取三个 key → `PUT /api/storage/:key`（仅限该浏览器本机数据，一对一导入）。
- 不做自动双向同步，避免版本混乱。

## 9. 部署与运行

- `web/` 构建产物 `web/dist` 由 Express `express.static` 托管；`/api/*` 由 Express 路由。
- **SPA fallback**：非 `/api` 路径回落 `index.html`（深链 `/village/xxx` 不 404）。
- 启动命令：`node server/index.js`（生产）；本地开发仍 `pnpm dev`（Vite，local 模式）不受影响。
- **本地 remote 模式开发**：`vite.config.ts` 配 `server.proxy` 将 `/api` 代理到 Express（默认 `http://localhost:3001`）。
- SQLite 文件路径由环境变量 `DATA_DB` 指定，默认 `server/data.db`；加入 `.gitignore`。
- `README.md` 补充生产部署章节；`.env.local.example` 增加 `VITE_STORAGE_MODE` 示例。

## 10. 受限数据与安全边界

- 服务端只存三类编辑数据；AI 地块 GeoJSON、影像瓦片、行政边界继续走静态文件，不进数据库、不公开分发（不变更现有硬约束）。
- 内部使用阶段不引入用户体系；API 仅限内网/本地访问（部署文档注明不暴露公网）。如需外网再评估 token 鉴权。
- 不记录隐藏原因、不上传任何源数据文件（现有约束延续）。

## 14. 遗留风险

- 同村并发编辑按最后写入胜出，多人同时改同村会互相覆盖（内部低频，接受；`updated_at` 已预留乐观锁位）。
- 保存动作异步化触碰 5 处既有调用点（§6.4），是回归风险点，实施时以全部单测 + 浏览器走查兜底。
- 预取/写盘失败若处理不当会退化为「静默空数据」（本次事故同款现象），必须走 §6.1/§11.7 的错误可见路径，禁止回退 localStorage。
- 迁移脚本一次导入后不维护，后续以服务端为唯一事实来源。
