# 地块成片划分 V1：龙江村重新划分经验总结

> 2026-08-19 龙江村（330604102014）地块划分从"算法聚类"改为"用户标注区域"全过程的复盘。
> 后续 12 个参保村的地块重新划分按本文件流程执行，避免重犯。

## 一、过程回顾（发生了什么）

1. **初版（dev-flow 算法路线）**：按需求实现成片聚类（200m 链式连通 + 500 亩上限切分 + 60~80% 覆盖区间），验收 16 项通过、质量审查修复 B1。用户介入提出异议。
2. **用户异议 1**：团单占比太少（算法自然覆盖 98.7%，团单仅 1.3%）→ 我建议恢复 60~80% 区间并改文档 → 用户转向"按参考图红框标注划分"。
3. **用户异议 2**：>50 亩未参保块不合业务逻辑（330604102015 块 782 约 88 亩等）→ 曾决定转参保。
4. **标注区域路线**：用户发红框参考图 → 红框检测与像素→经纬度映射反复迭代（多轮返工）→ 区域内归大户 → 100m 级联归并 → 未参保 83→0 → 忽略 50 亩单独出单规则 → 区域1 半区减半调整（maxLng）。
5. **最终结果**：区域1 558 块/886.93 亩、区域2 577 块/1175.88 亩、区域3 111 块/329.54 亩、团单 302 块（全部 ≤50 亩、一块一户、红框外）、未参保 0、覆盖 82.99%。

## 二、问题清单与根因（重点）

### P1 需求理解偏差（最大教训）
- **现象**：把"成片划分"做成算法题（聚类+指标），用户实际要的是"按业务/视觉形态的标注划分"（红框区域）。需求文档的 60~80% 覆盖、500 亩上限最终全部被用户推翻；50 亩单独出单规则也被"区域模式忽略"。
- **根因**：未先确认用户期望的划分形态，过早把算法规则写成需求。
- **避免**：开始前先复述"我理解的划分规则"（区域=大户、区域外=团单、未参保如何处理、面积上限、>50 亩处理），用户确认后再动手；规则与用户标注冲突时以用户标注为准并记录。

### P2 红框检测：骨架化/形态学收缩导致严重偏移
- **现象**：用 `binary_erosion` 提取红框中轴，红框被收缩 47~95px（约 200~400m），用户反馈"偏离很多"。
- **根因**：粗线红框的稀疏段被侵蚀剥掉，边界整体内缩。
- **避免**：红框提取用**原始像素簇外轮廓**（cv2.findContours + approxPolyDP），禁骨架化/侵蚀收缩；检测后用叠加图验证（检测线 vs 用户红线）。

### P3 像素→经纬度校准：假设视图参数会错
- **现象**：假设村级 fitBounds（zoom 15.1）映射偏差大；网格搜索匹配率仅 41%~57% 时仍继续使用。
- **根因**：用户截图的视图范围（zoom/center）未知，凭假设映射。
- **避免**：校准后必须做 **project-check**（把全部地块 label 投影到用户图上，确认与图中地块重合、无系统性偏移）；匹配率低时要检查检测点质量（误检集中在山体/水体），不要带病使用。

### P4 过度延伸/归并
- **现象**：200m 链式延伸吸光 99% 地块（用户否）；100m 归并把 83 块未参保全转参保（用户接受但属激进决定）。
- **根因**：延伸阈值未先与用户确认边界。
- **避免**：归并/延伸规则先给用户明确量化（如"红框外 100m 内归大户"），用户确认后再固化。

### P5 需求规则与标注的优先级
- **现象**：区域外 >50 亩单块（1424，51.36 亩）先按 50 亩规则单独出单一型保单，用户明确"忽略 >50 亩单独出单规则，只按参考图划分"。
- **避免**：标注区域为权威归属；50 亩分类等全局规则在区域模式下的取舍先与用户确认，不要擅自套用。

### P6 验证方式
- **现象**：用视觉模型（describe_image）判断颜色/对齐多次误判（把粉/蓝看混、说"框内蓝点"实为色觉错误）。
- **避免**：对齐/归属用**定量统计**（框内色点计数、成片最近邻、团单范围），视觉模型只做辅助初判。

## 三、后续 12 村标准流程（照此执行）

1. **收图**：用户发某村参考图（红框标注大户区域），确认村代码与红框数量。
2. **复述规则**：先文字复述（区域内全部地块含未参保归大户 → 区域外 100m 级联归并 → 其余一块一户团单 → 未参保可转参保 → 忽略 50 亩单独出单），用户确认。
3. **红框检测**：cv2 原始像素簇外轮廓（禁骨架化）；叠加图验证与用户红线重合。
4. **映射校准**：检测地块点 + label 网格搜索匹配；**project-check 强制验证**（label 投影 vs 图中地块，无系统性偏移才继续）。
5. **归属计算**：区域内全部 → 大户；区域外 100m 级联归并；其余团单；未参保按用户决定（可全转参保）。
6. **可视化确认**：生成划分图（大户色/团单/未参保 + 红框），给用户确认（红框对齐、区域完整无零星、团单范围、数量比例）。
7. **固化**：配置落盘 `scripts/data/{村代码}-regions-2025.json`（区域多边形 + mergeMeters + maxLng 可选），prepare 区域模式生成确认/fixture，验证（成片、一块一户、无重复、团单红框外、确定性）后提交。
8. **同步文档**：需求文档 A4 记录确认结果与最终统计。

## 六、大钱村（第 2 村）追加经验（2026-08-19）

第 2 村（330604102015，2 个红框）按流程走，新发现以下问题与修正，已并入技能：

### N1 每个村的归并规则可能不同（关键）
- **现象**：龙江村用户接受 100m 级联归并（"红框临近的地块也要纳入"）；大钱村用户明确"黑框外的都是团单，延伸多了"——**无归并**（红框内=大户、红框外=团单）。
- **教训**：归并/延伸规则**不是全局默认**，每个村必须单独确认（"区域外是否需要归并、阈值多少"）；不能复用上一村规则。
- 落地：区域配置 `scripts/data/{村}-regions-2025.json` 的 `mergeMeters` 按村设置（龙江 100、大钱 0），prepare 按配置驱动。

### N2 多边形顶点乱序导致 in_poly 错误
- **现象**：cv2 approxPolyDP 对碎片化红色轮廓输出乱序顶点（如左框 [(544,56),(172,58),(177,346),(544,330),(485,329),...]），in_poly 判断大面积错误（大户2=0 块、大户1=741 块）。
- **教训**：用户画的长方形红框用 **bbox 矩形**（经纬度矩形 in_rect）更稳；用多边形时必须先验证顶点是绕序（cv2 contour 顺序），或可视化叠加验证后再归属。
- 大钱村最终用 bbox 矩形（2 框 x[167,545]/x[545,924] y[47,348]/y[48,342]），归属正确。

### N3 截图村识别
- **现象**：先用 433 个检测点匹配 13 村 label，龙江村 46%、大钱村 29%——低匹配率不能定论，需结合地名标签（盘窝里/良夹岙=龙江周边）与用户确认。
- **教训**：匹配率仅作候选排序，最终村代码以用户确认为准；检测点噪声（山体/水体）会压低匹配率。

### N4 一般未参保规则统一
- 区域内/归并的未参保 → 转参保归大户；区域外未参保 → 保留（龙江村 83 全在区域内/归并 → 0；大钱村 37 转/10 保留）。同一规则适配两村，龙江村产物字节级不变。
- 未参保保留清单（大钱村 10 块）需用户确认。

### N5 流程有效性确认
- project-check（label 投影 vs 图中地块）大钱村一次通过，映射无返工——该防线有效，务必每村执行。
- 每村两轮确认闭环：方案图确认（红框对齐+数量）→ 固化 → A4 同步。大钱村 1 轮调整（去归并）即定稿。

## 七、检查清单补充（每村必过，v2）

- [ ] 归并规则（mergeMeters 0/50/100/无）已按村确认（勿沿用上一村）
- [ ] 红框用 bbox 矩形或已验证绕序的多边形（勿用乱序多边形）
- [ ] 村代码以用户确认/地名佐证为准（匹配率仅辅助）
- [ ] 未参保保留清单用户确认

## 五、遗留认知（后续村注意）

- 用户截图视图多样（不同缩放/平移），每张图必须独立校准，不能复用龙江村的 zoom/center。
- 小村（如白沙 232 亩）可能整个红框区域都进大户或全团单，区域模式天然自适应，但面积/占比记录要核对。
- 未参保集合在区域模式下可变化（龙江村 83→0）；每村未参保处理（保留 or 转参保）由用户拍板并记录。
- 团单/大户的比例无硬指标，用户按图确认；"减半"等量级调整时先算好数字给用户看再改。
