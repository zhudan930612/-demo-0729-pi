# ADR-0010：运行数据随仓库分发（非影像数据入 git/git-lfs，影像瓦片仍脚本生成）

状态：采纳（2026-08-24 拷打确认）

## 背景

曾长期把 `web/public/data/`（行政边界、村界、AI 地块、manifest）与 `web/public/tiles/`（影像瓦片）整体 `.gitignore`，由 `scripts/prepare-all.sh` 从 LFS 源数据（约 2.1G）生成。克隆者**必须 `git lfs pull` + 跑脚本**才有边界/村界/AI 地块/影像，门槛高；且克隆后依赖 Python 环境与 Delineate 产物。

用户核心诉求：**边界/村界这类稳定数据应一次性生成后直接可用，不应让协作者再跑脚本生成**。

## 决定

- **非影像运行数据随仓库分发**：AI 地块、行政边界、人工地块、地块可见性、业务静态 —— 入 git，克隆者克隆即用，**无需本地跑脚本生成**。
- **村界 villages（293M）走 git-lfs**：避免撑大仓库，克隆者 `git lfs pull` 取回（比跑脚本省事、不撑仓库体积）。
- **行政边界 / 村界随仓库公开分发**：放宽原「行政边界不得公开分发」受限约束（与 AI 地块一致，见 ADR-0009）；保留「不得描述为确权/承保/测绘成果」表述纪律。
- **影像瓦片仍脚本生成**：tiles 781M（吉林一号影像，受限）不入 git，克隆者看影像仍须本地跑 `prepare-rs-tiles`（因体积与受限）。
- **前端加载来源**：人工地块/可见性从 `/business/*` 静态文件加载（不再 localStorage），经本机写入端点落盘（ADR-0008）。

## 原因

- 行政区划、村界、AI 地块、业务数据为**稳定、非高频变化**的运行产物，一次性生成后随仓库分发即可，克隆者不必重复跑脚本，显著降低使用门槛。
- 村界与影像瓦片**体量大**（293M / 781M），全入 git 会显著膨胀仓库、拖慢克隆；村界作为稳定数据用 git-lfs 平衡「直接可用」与「仓库体积」，影像瓦片因体积+受限保留脚本生成。
- 用户明确要求行政边界/村界随仓库公开分发（与 AI 地块一致），授权合规风险记录在案（见触发重开）。

## 被否方案

- **整体维持脚本生成（现状）**：克隆者门槛高，违背「稳定数据一次性生成直接可用」的诉求。
- **全部非影像数据（含村界）直接入 git**：仓库增 293M+，膨胀过大；村界改用 git-lfs 平衡。
- **影像瓦片也随分发**：781M + 吉林一号影像受限，不现实。
- **仅人工地块随分发、边界/村界仍脚本**：克隆者仍看不到边界/村界，未能满足「克隆即见完整地块体系」诉求（被用户否）。

## 触发重开

- **数据授权合规（未核实）**：AI 地块、行政边界为真实农田/行政边界数据，随仓库**公开**分发的授权/版权合规**未经核实**（用户明确要求）。若后续合规审查发现不可公开，应**重开并撤回**公开分发，改回受限目录/仅本机。
- 若引入真正的后端同步/多人实时协作，或要求按地块级合并，则重开 ADR-0008 及本决定的分发协同部分。
- 若影像瓦片获得允许随分发、或其体积/受限不再构成障碍，可重开本决定的「影像仍脚本生成」。
