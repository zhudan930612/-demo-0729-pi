## 1. 目标与已确认范围

当前保单、种植档案和地块详情业务数据**只覆盖龙江村 `330604102014` 一个村**；演示时进入其他村无业务可看。本计划把「AI 地块识别 → 参保确认 → 4+1 保单造数 → 前端按村加载」整条链路从单村推广到**影像覆盖的多个村**，使演示时可随机进入多个村查看地块详情、种植档案、保单与分户清单。

### 已确认决策

- 地块数据来源：**跑 Delineate Anything v2** 为影像覆盖村批量生成（用户已确认）。
- **龙江村现有数据完全不动**：现有 `policy-v1.json`/`cultivation-v1.json`/`parcel-confirmation-v1.json`/`330604102014.geojson` 保持原样、原文件名，参数化脚本对龙江村仍按原文件与规则运行，重跑不覆盖现有产物（龙江村保留手工确认清单与现有 fixture）。
- **其他村数据全部参考龙江村规则生成**：同一套造数逻辑（4+1、50 亩、90% 覆盖、身份证/银行卡规则），四区划分对非龙江村使用归一化坐标的通用四象限规则（确定性、可复现），不依赖龙江村手工截图。
- **先 1 村全链路验证，通过后再放量**：先选一个影像覆盖村（建议清潭村 `330604102016`，相交 100%）跑完「裁片 → 推理 → 导出 → 确认 → 造数 → 前端加载」全链路并验收，验证通过后才继续其余村（分批跑）。
- 目标村：以实测影像相交为准，章镇镇 8 村（含龙江）+ 三界镇 5 村 = **13 个有效覆盖村**（相交比例 >5%）；龙浦村 3.4%、杭浦村 0.5% 相交过小，识别产出地块极少，本期不做。文档历史口径「章镇 11 + 三界 6 = 17」为 2026-07-29 初测，与本次实测（15 村相交）的差异以本次实测为准。
- 前端数据形态：**每村独立 fixture 文件**（`/business/policy-{村代码}.json` + `/business/cultivation-{村代码}.json`），前端进入村级时按当前村代码加载，彻底避免跨村地块 ID 冲突与数据串村。
- 保持既有业务规则：4+1 保单结构（4 单一型 + 1 分户清单）、50.00 亩分类阈值、90% 参保覆盖、身份证/银行卡生成规则、机构中立，全部沿用，不因多村化放宽。

### 明确不做

- 不做人工地块的保单关联（人工新增地块默认无保单，沿用现状）。
- 不做无影像村的业务数据（无地块即无保单基础）。
- 不修改保单业务 schema 版本（仍为 `policy-v1` / `cultivation-v1`），每村 fixture 各自带 `villageCode`。
- 不引入后端同步、多人协作、导出导入。
- 不改变台风、天气、预警等其他模块职责。

## 3. 目标架构

```text
05-遥感数据/源TIF
   │  prepare-parcel-pilot.py prepare --village {code}
   ▼
05-遥感数据/parcel-pilot/{村代码}/images/{村名}/   ← 裁片（村界外扩 128m）
   │  delineate.py -b batch-{批次}.yaml（conda 环境）
   ▼
.../delineated/{村名}.gpkg
   │  prepare-parcel-pilot.py export {gpkg} --village {code}
   ▼
web/public/data/parcels/{村代码}.geojson          ← 每村地块（ID 1..N，村内唯一）
   │  prepare-policy-confirmation.py --village {code}
   ▼
web/src/data/parcel-confirmation-{村代码}.json    ← 参保确认（四区 + 一块一户）
   │  generate-policy-fixture.py --village {code}
   ▼
web/src/data/policy-{村代码}.json + cultivation-{村代码}.json
   │  （脚本同时写 web/public/business/ 同名文件）
   ▼
前端进入村级 → policyRepository 按村代码加载对应 fixture
```

关键设计：**一切产物按村代码命名/隔离**，前端按当前村加载，不做跨村合并。

## 4. 分阶段实施

### M1 参数化 `prepare-parcel-pilot.py`

- 新增 `--village {村代码}` 参数（默认 `330604102014` 保持向后兼容）。
- `village_feature()` 改为从 `--township {乡镇码}` 或自动扫描 `web/public/data/villages/*.geojson` 按 `code` 匹配（支持村码前缀 ≠ 乡镇码）。
- `SOURCE_TIF` 保持单源影像；`WORK`/`INPUT`/`OUTPUT`/`FRONTEND` 全部按村代码派生。
- `prepare` 裁片、`export` 裁回村界逻辑不变（已通用）。
- 输出每村 `{村代码}.geojson`，地块 ID 从 1 开始村内排序。

### M2 批量推理与地块导出

- 为 12 个新增村逐个 `prepare` 生成裁片（每村数分钟）。
- 建立 `05-遥感数据/parcel-pilot/batch-villages.yaml`，`include` 列出全部待推理村。
- 用 conda 环境串行跑 `delineate.py -b`（预计 8~9 小时；可分段跑，每段一个 yaml）。
- 逐个 `export` 导出前端 GeoJSON；`enrich` 校验面积字段。
- 期间输出按村记录地块数量、总面积，作为后续参保覆盖检查输入。

### M3 参数化造数脚本

**M3.1 `prepare-policy-confirmation.py`：**
- 新增 `--village`，`SOURCE`/`OUTPUT` 按村派生。
- `region_index` 改为**基于归一化坐标的通用四区划分**：以村界 bbox 归一化 u/v，按「西部带 / 北部带 / 西南带 / 东部带」四象限规则（沿用龙江村分区思想的几何化版本），不再依赖龙江村具体坐标。
- 未参保地块数：保持「全村地块 × 10% 向下取整」的固定规则；为**可复现**，按地块 ID 取模的确定性规则生成（如 `id % 19 == 0` 之类，数量自动落在 10% 内）——替代龙江村手工确认的 83 块清单。
- `assignmentModel` 保持 `four-approximate-regions-plus-one-parcel-roster`。
- 输出 `parcel-confirmation-{村代码}.json`。

**M3.2 `generate-policy-fixture.py`：**
- 新增 `--village`；从 villages 文件反查村名；`villageCode`、输出路径按村派生。
- `party_name`：前 4 户（四个经营区大户）不再用龙江村固定名单，改为确定性生成（2~3 汉字、全村不重复），与清单户共用名字生成器。
- `identity_number`：地区码按村所属县区推导（章镇→`330604`，三界→`330683`）。
- 清单项编号前缀：龙江 `LJ-` → 改为 `{村代码后 4 位}-` 或继续用 `itemNo` 序号即可（需求未要求特定前缀，界面不展示该编号，可保留纯序号）。
- 保单号 22 位数字保持「项目内唯一」：多村分别生成时以村代码片段 + 序号保证不冲突。
- 输出 `policy-{村代码}.json`、`cultivation-{村代码}.json`、`policy-{村代码}.report.json`，同时写 `web/public/business/`。
- `web/src/data/` 保留龙江村原文件名（`policy-v1.json` 等）以兼容现有测试与校验；新增村用带村码文件名。**决策点见 4.4。**

**M3.3 `validate-policy-fixture.py`：**
- 改为 `--village` 参数化，遍历所有有产物的村逐一校验；1533 硬编码改为读取 parcels 实际数量。

### M4 前端按村加载

- `policyRepository.ts`：
  - 新增 `loadPolicyFixture(villageCode)` / `loadCultivationFixture(villageCode)`；URL 变为 `/business/policy-{code}.json`、`/business/cultivation-{code}.json`。
  - 保留无参版本加载龙江村（或默认村），兼容现有测试。
- `policySelectors.ts`：`parcelPolicyContext` 等函数**保持按 parcelId 查**——因为 fixture 本身已按村隔离，只要确保当前村加载的是当前村 fixture 即可，无需改 selector 签名（最小改动）。
- `MapView.vue`：
  - `loadBusinessData()` 改为进入村级时按 `crumb.code` 加载；切村时重新加载并校验 `fixture.villageCode === 当前村`。
  - 无业务数据的村（无 parcels / 无 fixture）：保持现状——详情打开显示「暂无关联保单」空状态。
  - 加载失败与当前不匹配时降级为空 fixture，不报阻断错误。

## 6. 验收标准

1. `python scripts/prepare-parcel-pilot.py prepare --village {任意影像村}` 与 `export` 可生成该村 `web/public/data/parcels/{村代码}.geojson`，ID 村内唯一、含 `area_m2`/`area_mu`/标注点。
2. `prepare-policy-confirmation.py --village {村}` 输出覆盖该村全部地块、唯一、参保比例 ≥90%，四区 + 一块一户模型。
3. `generate-policy-fixture.py --village {村}` 输出满足全部既有规则：2025 当前保单严格 4 单一型 + 1 清单型、50 亩分类、无重复承保、金额精度、姓名/证件/银行卡校验。
4. 龙江村重跑结果与现有 fixture 完全一致（哈希或业务字段一致），确认参数化未破坏既有行为。
5. `validate-policy-fixture.py --village {每个村}` 全部通过。
6. 前端进入任意有业务数据的村：地块详情、种植档案、保单、分户清单正常；切村后数据不串（A 村地块详情不会显示 B 村保单）。
7. 进入无业务数据的村：不报错，详情显示既有空状态。
8. `pnpm --dir web test`、`pnpm --dir web build`、scripts 单测、`git diff --check` 全部通过。

| 12 村推理总时长 8~9 小时 | 周期长 | 分批跑、每批独立 yaml 与 log；**先 1 村全链路验证通过后再放量**（用户已确认） |
| 部分村相交比例低（新南 15%、湾头 18%），识别地块可能偏少或漏 | 该村业务数据稀疏 | 先跑完看数量，若某村地块 <100 则评估是否保留；验收时记录每村地块数 |
| 三界镇属嵊州（330683），身份证地区前缀不同 | 校验失败 | identity_number 地区码按村所属县区参数化 |
| 村码前缀 ≠ 乡镇码 | 裁片/村名反查失败 | 统一从 villages 文件按 code 匹配，禁止前缀推导 |
| `region_index` 几何化后四区边界与龙江村实测不同 | 影响龙江村现有数据 | **龙江村不动**：现有 confirmation/fixture 保留；非龙江村使用通用四象限规则（用户已确认） |
| 前端全局 fixture 依赖（现有测试引用 policy-v1.json） | 测试破坏 | 保留龙江村原文件名兼容，新增村用带村码文件名 |
